## 已知限制與審查重點

1. 一筆提交日誌為業務來源，其他表為副本；這是避免多表半寫入的設計，不是宣稱Sheets具備跨服務交易。
2. 只保留已提交業務事件，驗證拒絕不寫入成功日誌。伺服器未開始提交的錯誤監控及更完整的失敗稽核仍需後續補強；結果未知靠前端保留原請求與日誌重播對帳。
3. 日誌全量重播與副本逐列重建適用目前原型規模，沒有大資料量效能保證；後續需快照、分頁與增量投影。
4. 相同RequestID重播原結果；前端再重新讀取現在狀態。不能因重播舊版回應而再次覆寫新資料。
5. 未確認請求保存在同分頁sessionStorage，不保證關閉分頁後仍在；可能包含照片。金鑰只在使用者選擇記住時進localStorage。
6. 照片建立後如果提交未確認，可能留下私人孤立檔；本版不自動刪除，避免刪到其實已提交的照片，後續需孤立檔清冊。
7. 共用金鑰無法可靠歸屬操作人；紀錄明確標示「共用金鑰」。
8. config.js未指向任何現用後端，必須先完成隔離schema4後端測試與資料移轉，再安排前後端共同切換。不可直接把main合併視為已完成部署。
